# SlopBot release evidence

## Source intent and claim boundary

The user confirmed this scope on 2026-10-09 after a release-boundary interview. The whiteboard's stage, game-mode, contribution, animation, and video topics were candidate areas, not approval to ship every workflow.

The [fifth-character video plan](https://app.notion.com/p/Creating-the-fifth-SlopArena-character-video-plan-3f410b677667814895ffefe5e2538dcf) describes a creation diary, not a tutorial. Animation is the main story and current bottleneck; separate videos explain the game and agent setup. SlopBot's release must precede public recommendation of the skill, but does not implement video production.

The planned diary follows a Tripo-generated model, Mixamo rigging, Unity import, sourced animations including a purchased Unity pack, one difficult animation adjustment, Slop Editor attack authoring, Training correction and a sequence, splash art, VFX, and final gameplay. These are the creator's planned tools and footage, not mandatory providers or assets for every SlopBot user. Splash/VFX creation can appear in the diary while remaining an optional external handoff in the skill.

The character name, approved kit, model, exact animation pack/clips, and optional presentation assets are chosen during the character run. They are not unresolved release-scope decisions.

## Public-bundle smoke

Exercise the distributed `skills/` source, not merely a private assistant session that already knows the project:

- Load SlopBot and required helpers through the exercised harness's normal skill mechanism; record the harness, available tools, prerequisites, and configured project roots.
- Confirm orientation explains the supported character journey and resolves relevant public documentation/helper references without private BMAD/workspace files or personal paths.
- Ask for an out-of-scope stage, game-mode, or contribution task; observe an honest documentation route without starting implementation.
- Exercise guided and fast usage against approved work. Observe their different pacing and identical approval/acceptance gates.
- Exercise one actually unavailable capability. Observe a concrete handoff or blocker, then confirm completion depends on inspecting a real result rather than an assumed tool success.
- Interrupt and resume a character task. Recover approved choices and the next action; change a relevant input and confirm obsolete evidence is not reused as current acceptance.

These are release demonstrations, not a requirement to create a permanent mock-heavy test suite or a cross-harness certification matrix.

## Next-character acceptance

- Agree the humanoid character's complete kit and required presentation. Resolve every required canonical slot intentionally; approved clip/move reuse is allowed, broken or filler slots are not.
- Obtain and record real model/rig/clip sources and applicable licensing. Account setup and external service actions remain explicit handoffs; no unapproved installation or spending.
- Exercise the imported character and a bounded existing-clip adaptation on its actual runtime surface. Preserve an observed before/change/after comparison that demonstrates the intended correction.
- Author the approved attacks in Slop Editor/Ability Lab. Observe at least one gameplay expectation, correction, and repeat of the same situation in Training, plus the intended kit interactions needed to establish completion.
- If splash art or VFX integration is selected, observe the asset in its actual consuming UI/gameplay surface. Not selecting optional assets does not fail the release.
- Inspect and cook current source through the supported path; verify `manifest.json`, `character.runtime.json`, `poses.bin`, and `client.bindings` and their identity/hash/dependency agreement. Require valid, non-stale inspection and the exact local admitted roster requirement.
- Exercise the agreed kit through applicable local gameplay using that persisted package, following the adopted repository acceptance rules. A transient editor draft, source-only probe, previous valid cook, compile result, or asset import alone is not acceptance.
- Record enough source/package identity and observed results to tie the footage and verification to the accepted content. Reuse evidence across checks when it answers the same question; retain useful before/after and gameplay proof rather than every intermediate log.

If a required step remains blocked or the complete kit is unfinished, the release gate has not passed. The diary may discuss roughness; the skill must not call blocked required behavior complete.

## Claims the evidence permits

The next-character run proves the supported process and tool path actually exercised by the creator. It does not prove independent technical-newcomer success, execution compatibility with every harness, custom-rig support, online match agreement, deployment, or publication. Independent newcomer trials and additional harness runs are not gates for this release, and must not be implied by its public wording.
