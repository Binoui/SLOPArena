# SlopBot Character

Use this helper for the character work owned by the selected SLOPArena checkout. The entry skill `slopbot` owns approvals, interaction mode, selected checkout, and the small `.slopbot/<package-or-goal>.md` progress record. If invoked directly, first load those shared instructions from the harness skill loader or sibling `../slopbot/SKILL.md`; if unavailable, stop rather than bypassing them. Resolve every project document below from the user's selected checkout, never from this installed helper's directory or an author's workspace path. Work only within the approved character scope; a missing tool means an explicit user handoff or blocker, not a claim of action.

## Establish the agreed character and assets

Start with the user's actual goal, existing package/source, approved concept or kit, and progress record. Resume at the unresolved need; do not repeat settled design decisions. If the kit is not approved, use game-root `docs/characters/character-kit-design-principles.md` to agree a humanoid fighter's role, movement/recovery, eight normals, four specials, intended interactions, and desired presentation. Record the decisions and required asset roles before integration. Game-root `docs/characters/adding-a-new-character.md` owns implementation and acceptance; `docs/characters/character-import-checklist.md` is a checkpoint, not a substitute.

For every model, rig, animation clip, image, or effect, identify the actual source and exact intended asset; record provenance, creator/source URL or supplier, applicable license, attribution, and whether redistribution into repository/package is permitted. A service/library handoff requires the user to select/provide the assets and licensing evidence. Do not assume a license, generate or fetch assets, author a full model/custom rig/original motion, or silently include non-redistributable content. Preserve source files and Unity `.meta` files. If an ordinary humanoid rig, required clip, license, or supported tool is missing, state the concrete input and expected proof needed from the user; inspect the returned asset before resuming.

Map the concept onto existing gameplay primitives and the current Shared implementation, not an invented mechanic. Confirm a proposed operation/capability is supported by current project documentation/source before relying on it. If an essential interaction is unsupported, name it, pause that branch, and request a separately scoped engine task; present alternatives only as options for approval. Author the agreed package gameplay through existing primitives; do not substitute a different design or extend Shared/server engine code as part of integration.

## Integrate source and author the kit

The project has distinct owners: `package.json` for identity/version/creator/license/attribution/dependencies, `character.json` for gameplay source and presentation IDs, and `CharacterAssetCatalog.asset` for Unity rig and semantic clip bindings. Source package location and the authoring-ready template seam are documented in game-root `docs/characters/adding-a-new-character.md` and `docs/systems/ability-lab.md`. Do not invent a package-creation button: current docs identify `AbilityLabPackageWorkspace.NewPackage` as the creation seam but no user-facing creation flow. If no supported tool or authorized operator can invoke that seam, hand off the approved package specification and required result; do not create an ad hoc package or claim creation.

Bind real clips to exact semantic IDs on the actual imported Humanoid rig; preserve unique deterministic pose-track IDs and resolve Avatar/binding diagnostics instead of borrowing another fighter's fallback. If model cleanup or rig repair is needed, name that external/separate scope and route to game-root `docs/characters/character-model-polish.md`. Optional splash art/VFX are supplied/sourced only: verify ownership and the actual consuming surface/binding, and leave them out if not selected. Once selected as required presentation, their integration must be verified rather than silently omitted.

Resolve all sixteen canonical grounded/air slots deliberately from the agreed kit. Approved aliases and move/clip reuse count; a smaller number of independent source entries is not itself an incomplete kit. Use the compiler/inspect resolved projection and approved semantics, not counts or labels alone, to judge coverage. Starter template values are not approved moves. Keep controls/labels distinct from persisted slot identities. Use the existing Slop Editor/Ability Lab Moves workspace for live drafts, timeline, source-stage fields, SceneView overlays, supported operation inspectors, and Undo; do not guess controls or create a second mapping. Through supported Shared/Training paths, observe timing, contact/miss, hitboxes, damage, recovery, movement and selected mechanics; change the relevant draft input and retest. Shared/server owns outcomes; if a mechanic cannot be authored through existing primitives, pause at the engine-task boundary.

## Inspect, cook, admit, and play

Before cooking, resolve supported operations and Editor ownership from game-root `docs/contributing/unity-cli.md`; command examples are not permission to bypass ownership or require an author's private workspace. Discover available supported commands and use `sloparena.character.inspect` read-only on the actual package when authorized. Resolve identity, canonical-slot, source/catalog, rig, dependency, stale-input, and structured diagnostics. If the required tool/owned route is unavailable, hand off the exact package and expected inspect evidence; do not report verification.

Persistence is through the documented Ability Lab **SAVE + COOK** path (or its supported native command flow), not raw edits to generated output. A successful cook must identify the exact current package and its four fresh payloads/hashes; a failed cook is a failure even if it preserves an older valid artifact. Re-inspect after changes and ensure evidence refers to current source, rig, catalog, and dependencies. Do not edit cooked payloads or generated catalog cache as source.

After a successful current cook, complete the applicable focused compiler/catalog/package checks and kit regression evidence specified by game-root `docs/characters/adding-a-new-character.md` and `docs/testing.md`. Test, change, and retest behavior that failed or needed tuning; report actual observations and limitations. Add or refresh exact roster admission only through the documented workflow and after required checks/presentation are valid. Verify package identity/version/hashes/dependencies and the exact local roster requirement against fresh content; source-only discovery or a transient draft does not count.

Open the accepted cooked package in Ability Lab to check identity, slot projection, semantic bindings, preview, and diagnostics; exercise Training and applicable local gameplay with that same persisted package. Confirm the roster selects it and the complete agreed kit is actually exercised using admitted content, not an in-memory draft, stale cook, or prior fighter. Record observed checks, input identities/hashes, outcome, and blockers. No online play, publication, or broader release claim follows from local acceptance.

## Resume and handoff

On resume, compare recorded approvals, kit, asset provenance, source/package identity, bindings, cook hashes, roster requirement, and test/play evidence with current files and diagnostics. Invalidate only checks whose inputs changed. Preserve valid prior work. A useful handoff names the exact missing asset/tool/permission, the owner or supported documented route when known, the expected output/evidence, and the next step after it is supplied; never turn instructions into claimed completion.
