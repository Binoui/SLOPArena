- (direction) Create a reviewable implementation spec from the accepted Replay v1 design; implementation, commits, publication and deployment remain separate tasks.
- (note) Express derivation from rich conversation and adopted project documents; activation hooks and persistent facts are empty. With no configured initiative, keep the loose spec in public project docs rather than create private planning/configuration dependencies.
- (decision) Adopt docs/plans/2026-10-13-replay-v1-design.md, docs/adr/0033-gamehost-input-replays-with-shared-playback.md and CONTEXT.md as load-bearing companions; their accepted scope and vocabulary remain authoritative.
- (capability) CAP-1: Players can review authoritative online PvP gameplay; success is complete or explicitly partial reconstruction of real two- and four-fighter Matches with the captured host decisions.
- (capability) CAP-2: Players receive trustworthy compatibility/validation outcomes; success rejects incompatible or malformed files and stops at the first failed recorded authoritative check with tick/reason while preserving the file.
- (constraint) Record exact initialization, absolute ticks and selected inputs before Shared consumes them; retain roster/input membership, immutable cooked content/poses, arena/rules/tuning and original provenance. Do not use InputRelay or lossy network snapshots as the tape/checkpoint.
- (constraint) Whole-Match Linux GameHost to supported Unity Windows parity is unproven and gates shipping. Derive configurable byte/tick/queue/decode/upload budgets from prototype measurements before backend integration.
- (capability) CAP-3: Players can inspect combat; success demonstrates pause, speed, forward tick-step, waiting seeks, fighter selection/orbit/zoom, responsive paused camera/UI and presentation reset without stale effects or historical seek audio.
- (capability) CAP-4: Participants can retrieve recent recordings after relaunch or from Results; success shows Match ID and pending, available complete/partial, unavailable reason or expired status even when no file exists.
- (capability) CAP-5: Players can download and import portable Replay files for bug reports; success imports compatible local files after backend expiry without contacting the backend.
- (capability) CAP-6: Participants can share one unlisted link per Match; success allows any participant to create/regenerate/revoke it, enforces participant or active-link access, invalidates old link retrieval on revoke/regenerate, and leaves downloaded copies usable.
- (capability) CAP-7: Finished recordings survive host/backend interruptions within budgets; success retries durable finalized artifacts after restart with original provenance and immutable idempotent receipt, preserves queued files when full, and reports newer unavailable recordings.
- (capability) CAP-8: Recording/storage policy remains bounded without changing gameplay; success retains valid limit/cancellation prefixes where capacity allows, expires backend retrieval 30 days after recorded Match termination, and never extends expiry on retry or link renewal.
- (decision) Live spectators, historical runtimes, checkpoints/instant seeks, free camera, Training/CPU/Ability Lab recording, ongoing-Match crash recovery, browser playback and app launch remain outside v1.
- (question) The accepted design stores compressed bytes in PostgreSQL; later discussion recommends private managed S3-compatible bytes with PostgreSQL metadata. Explicit adoption of that storage revision and provider selection remain unresolved; propose it for review without rewriting the accepted ADR.
- (assumption) Propose storage-neutral immutable artifact identity (Match ID plus digest), metadata schemas and backend-gated downloads so the recording/viewer contract is independent of the storage revision.
- (assumption) Propose one Master upload operation carrying bounded metadata and artifact bytes; Master authenticates current owning host, streams/hashes bytes into configured storage, then marks available only after object persistence and metadata commit. Handle retries and orphan cleanup without overwriting conflicts.
- (constraint) Master enforces the original recorded termination deadline on every retrieval; object cleanup does not define access expiry. Backend-gated private-object streaming preserves link revocation without outstanding reusable object URLs.
- (assumption) Propose Replay setup/tick/footer semantic fields, a checked Shared playback session exposing fixed stepping and tick events, separate Match outcome/completeness/availability axes, and bounded decoding/seek work. Names, binary layout, validation coverage/cadence and measured numbers are frozen during the contract/prototype gates.
- (constraint) One owner controls Shared schema/validation and GameHost capture; Unity and Master agents consume versioned fixtures/contracts. Backend integration waits for parity and measured budgets; independent viewer/backend scaffolding may be prepared concurrently after contracts freeze.
- (constraint) Parallel implementation uses distinct file ownership and respects existing working-tree edits; canonical Unity operations and plugin copy require each caller's own bounded gateway lease. Do not launch agents or operate Unity during this documentation task.
- (note) Current source confirms host selected input dictionaries are mutated by Shared ability admission and pre-Tick copy is necessary; LocalSimulationBridge exposes production simulation and respawn seams but is not already a full Replay viewer.
- (note) Human and agentic time ranges from discussion are unmeasured planning estimates, not acceptance criteria or delivery commitments; calibrate effort after the parity prototype.
- (event) Draft derivation input complete; eight stable capabilities and one unresolved architecture revision identified.
- (assumption) Clarify integrity derivation: the full-file SHA-256 is computed after encoding and carried in publication metadata/receipts; an in-file payload checksum must not include its own field. Backend downloads compare the expected artifact digest and local imports check container integrity/validation.
- (constraint) Copy candidate inputs before Tick and commit them only after a successful complete Tick/check; finalize at a synchronized simulation boundary rather than the external cancellation callback. Bound capture/finalization work and keep storage/upload/compression I/O out of the gameplay tick path.
